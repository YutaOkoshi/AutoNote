# アプリ内の自動アップデート（設計）

2026-11-19。現状の調査は作業用の `INVESTIGATION.md` の C 節（別 worktree、未コミット）にある。

## 目的と理由

利用者が何もしなくても、アプリが常に最新版になるようにする。いまは GitHub から zip を落として入れ替える手作業で、入れ替えのたびに macOS の許可（マイク、システム音声）が外れることもある。

## 利用者が決めたこと

- アプリ側で常に最新版にアップデートできるようにする。確認は 1 日に 1 回くらいでよい。
- 署名は自己署名（無料）でよい。
- PR、main へのマージ、リリースまで自動で進めてよい。

## ゴール

- 1 日 1 回、新しい版が出ていないかを確かめ、出ていれば取得して、じゃまにならないときに入れ替えて再起動する。
- 入れ替えても macOS の許可が保たれる。
- 設定で自動アップデートを切れる。「今すぐ確認」ができる。

## 非ゴール

- 差分更新、ベータ版の配信経路、巻き戻しの UI。
- Developer ID と公証（初回インストールの「このまま開く」は残る）。
- Sparkle の導入。

## アンチゴール

- 録音中・後処理中・翻訳中に入れ替えること。
- 署名を確かめずに入れ替えること。
- 更新の確認で、版の問い合わせ以外の情報を外へ送ること。
- 入れ替えに失敗してアプリが起動しなくなること。

## 方式（検討した 3 案）

1. **GitHub Releases を自前で確認して入れ替える（採用）**。依存が増えず、手で組んでいる `.app` と Xcode なしのビルドのまま作れる。入れ替えと失敗時の復旧は自前で書く。
2. Sparkle を入れる。入れ替えの実績はあるが、フレームワークと補助プログラムの同梱、入れ子の署名、appcast の生成と公開、EdDSA 鍵の運用が増え、Xcode なしの環境で動作確認が重い。
3. 通知だけ出して入れ替えは手作業。安全だが「常に最新版」にならず、許可が外れる問題も残る。

## 設計

### 署名の固定（前提）

- すべてのリリースを同じ自己署名の証明書で署名する。macOS の許可は「識別子と証明書」にひもづくので、版が変わっても保たれる。
- 手元のビルドとリリースで同じ証明書を使う。別々にすると、手元で入れたアプリとリリース版を行き来するたびに許可が外れる。いまの手元の証明書「AutoNote Dev」を取り出せるならそれをリリースにも使い、取り出しに利用者の操作が多く要るなら新しい証明書を作って手元にも入れる。
- 秘密鍵とパスワードは 1Password に置く（正）。GitHub Actions には Secrets として写しを入れる。リポジトリ・ログ・会話に値を出さない。
- `release.yml` は一時キーチェーンに取り込んで署名し、署名後に designated requirement が期待どおりかを検査する。期待する証明書のハッシュはリポジトリに置く（公開してよい値）。
- この署名に切り替わる最初の版だけは、これまでの配布物（その場かぎりの署名）からの入れ替えで許可が外れる。README とリリースノートに書く。

### 鍵の守り（2026-11-19 追記）

自己署名の鍵は漏れても失効できない。この鍵で署名してこのリポジトリのリリースに置かれた版は利用者の Mac に自動で入るので、鍵を読める範囲を最小にする。

- 署名用の Secrets はリポジトリ全体の Secrets ではなく、GitHub の Environment `release` の Secrets に置く。`release` の deployment branch は `main` だけに制限する。
- `release.yml` で署名するジョブだけが `environment: release` を使う。ビルド・テストなど他のジョブと `ci.yml` は鍵に触れない。PR や他のブランチのワークフローからは鍵を読めない。
- ワークフローの `permissions` は必要最小にし、外部のアクションはコミットの SHA で固定する。`pull_request_target` は使わない。
- アプリは確認先をこのリポジトリの releases に固定する（HTTPS。リダイレクト先のホストは GitHub のものに限る）。署名の一致・版が新しいこと・bundle identifier の一致をすべて満たすときだけ入れ替える。
- 確認先を差し替える環境変数は、開発用のビルド（debug 構成）でデータ領域を差し替えたときだけ効く。リリースビルドでは無視する。
- 鍵が漏れたときの手順（Secrets と 1Password の差し替え、新しい証明書への切替で全利用者の自動アップデートと許可が一度切れること、利用者への告知）は `docs/development.md` に書く。
- main のブランチ保護は変えない（自動マージの流れを止めないため）。推奨として `docs/development.md` に書くだけにする。

### 確認

- 起動時と、その後 24 時間ごとに、最後の確認から 24 時間たっていれば確認する。最後の確認時刻は保存する。
- `https://api.github.com/repos/<owner>/<repo>/releases/latest` を認証なしで読む。送るのは通常の HTTP 要求だけ。
- タグの版と `AutoNoteVersion.current` を比べる（数値として比べる）。新しければ、規則どおりの名前の zip とその SHA-256 を得る。
- 失敗（通信不可、制限）は静かに次回へ回す。

### 取得と検証

- zip をキャッシュ領域に落とし、SHA-256 を照合し、展開する。
- 展開したアプリの署名が有効で、**いま動いているアプリの designated requirement を満たす**ことを確かめる。満たさなければ入れ替えない。これが改ざんへの主な守りで、許可が保たれることの保証にもなる。
- 版が本当に新しいこと、bundle identifier が同じことも確かめる。

### 入れ替え

- 条件: 録音・カウントダウン・猶予中でない、後処理キューと翻訳のジョブが無い、メインウィンドウが開いていない。条件を満たしたときに自動で行う。満たさない間は待ち、メニューに「アップデートして再起動」を出して、利用者が選べば（録音中でなければ）すぐ行う。
- 手順: アプリが終了したあとに動く小さな補助（シェルスクリプトを切り離して起動）が、今のアプリを退避 → 新しいアプリを同じ場所へ移動 → 起動、を行う。移動や起動に失敗したら退避したものを戻して起動する。成功したら退避を消す。
- アプリの場所に書き込めないとき（権限）は自動では入れ替えず、メニューと設定に「手動での更新が必要」と出す。
- 再起動後、ログイン項目の登録が保たれていることを確かめる。

### 設定と表示

- 設定の「一般」に、自動アップデートのスイッチ（既定はオン）、今の版、最後に確認した時刻、「今すぐ確認」、状態（最新、取得中、再起動待ち、失敗の理由）。
- 外部通信の説明文に、更新の確認と取得を足す。`PrivacyCopyTests` を合わせる。

### 開発用

- 確認先の URL を環境変数で差し替えられるようにし、手元の偽のサーバーで E2E を回す（新しい版の検出 → 取得 → 検証 → 入れ替え → 再起動、署名が違う zip の拒否、ハッシュ違いの拒否、録音中の延期）。
- `autonote dev update --check` などの確認用コマンド。

## 作り手に任せること

版の比較の実装、補助スクリプトの細部、状態の持ち方、キャッシュの掃除、E2E の偽サーバーの作り。

## Lead が置いた判断（利用者の明示の指示ではないもの）

- 自前方式を採る（Sparkle を使わない）。
- 既定で自動的に入れ替える。メインウィンドウが開いている間は待つ。
- 手元のビルドとリリースで同じ証明書を使う。
- 署名の検査を、いま動いているアプリの designated requirement との一致で行う。
